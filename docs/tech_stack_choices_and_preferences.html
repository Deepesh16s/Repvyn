Our 30-second answer

What we say when a judge asks us to walk through the architecture. Everything after this is what we fall back on if they dig deeper.

So we're JavaScript from front to back. The web app's built in React with Vite, and it's served off Vercel's edge network, so it loads fast wherever you are. On mobile we're using React Native through Expo, and that side also pulls in wearable data from Android Health Connect — though we'll be upfront that the mobile app is a working prototype right now, not something we'd hand a judge to install; more on that later. Both the web app and the API talk to one backend — a Node and Express API we run on Render, with 102 REST endpoints spread across 16 route modules, plus a WebSocket for live chat. All our data lives in MongoDB through Mongoose: 26 collections, 53 indexes so lookups stay fast. For the things we didn't think we should build ourselves, we lean on outside services — Cloudinary handles images, Resend sends email, and notifications go out through standard web push. And every single request has to get past security headers, a locked-down CORS policy, rate limits, and token verification before it touches anything. The analytics you'd see in the app are actually just deterministic formulas we run right in the browser — there's no AI model anywhere in this, and that's on purpose. And nothing we write ships without going through GitHub Actions first: syntax checks, real tests against an actual in-memory MongoDB, a production build, and full browser tests end to end.

What happens when someone logs a set

We think the clearest way to show we understand our own architecture is to trace one real action through it, so this is the sequence we walk through when asked.

  1. React captures the set. Axios sends a POST to our API, attaching the login token in the Authorization header automatically.
  2. It travels over HTTPS to Render. We tell Express to trust Render's proxy, so it sees the user's real IP address — which our rate limiter needs.
  3. helmet adds our security headers, compression prepares to gzip the reply, and CORS confirms the request came from our own site.
  4. Our rate limiter checks this client hasn't gone over its allowance for that action.
  5. Our protect middleware verifies the token's signature and expiry, then reloads the user from our database — so deleting an account makes its token useless instantly.
  6. Our controller runs the logic and Mongoose validates the data against our schema: required fields, types, allowed values.
  7. MongoDB saves the document, using our indexed fields to keep lookups fast.
  8. Side effects fire: goals recalculate automatically, and a new personal record can award a badge and send a push notification.
  9. JSON comes back, React re-renders, and our deterministic engines recompute plateau, fatigue and weekly grade right in the browser.

Sending a chat message follows the same path through step 7 — we cap it at 60 messages per 5 minutes — and then our server looks up the recipient in its WebSocket connection registry and pushes the message down every connection that person has open, phone and laptop at once.

The five layers we built

This maps to the right-hand column of our technical approach slide, one layer at a time.

Clients

We built two apps — the React web app and an Expo mobile app — sharing one API. We keep business rules in one place, on the server, so web and mobile can never disagree about what's allowed. We'll say plainly: the mobile app today is a working prototype we run on our own device to prove the wearable-sync pipeline end to end, not yet a build we'd hand someone to install.

API

Express 5 with 102 endpoints across 16 modules we wrote. Login through JWT and Google, protection through helmet, CORS and 12 rate limiters, and a WebSocket at /ws/chat that requires a valid token to connect.

Offline layer — where we are and what's next

Right now our service worker handles push notifications only. What we've designed, and what we're building next, is an IndexedDB queue that a logged set writes to first, replayed by the service worker's Background Sync once connectivity returns. We picked IndexedDB over localStorage because localStorage blocks the page while it works, only stores text, and caps out at a few megabytes; IndexedDB is asynchronous, stores real objects, and holds far more. We picked Background Sync over a manual retry because the browser finishes delivery even if the tab gets closed. And replaying can't cause conflicts for us, because our workout logs are append-only — a user adds sets, they never co-edit a shared record.

If we're pushed on it: "Background Sync only works in Chromium browsers." — Correct, and our fallback for Firefox and Safari is retrying the queue when the browser fires its online event, which gets us the same result whenever the app is open.

Our deterministic intelligence layer

We built formulas, not a trained model. Our estimated one-rep max uses the Epley equation, our fatigue score is a weighted combination of five signals, and our volume ranges are percentiles of a user's own history — and every output we generate carries an evidence-strength tag. It all runs in the browser, so there's zero server cost, instant results, and nothing that can hallucinate. When someone asks us if this is AI, our answer is deliberately no — we weren't comfortable handing someone a recommendation about their own body that we couldn't explain.

Data and services

MongoDB holds our data — 26 collections, 23 models, 53 index declarations. We hand three jobs to outside services rather than building them ourselves: Cloudinary for images, Resend for email, and web push for notifications. Render runs our API, Vercel serves our web app, and GitHub Actions checks every change we make before it ships.

Frontend

What we shipped to run in the user's browser.

React

19.2

UI library

What it is
A library for building screens out of reusable components. When data changes, it redraws only the parts of the screen that need it.
Why we chose it
We wanted the largest ecosystem and talent pool, and the same way of thinking carries straight into React Native for our mobile app — one skill set covering both.
Alternatives we weighed
Angular, Vue, Svelte.
Why ours won
Angular felt like a heavyweight framework with a lot more boilerplate than we wanted. Vue and Svelte are excellent, but neither has an equivalent of React Native, so we'd have needed two different paradigms for web and mobile.
In our code
We load 16 screens lazily with React.lazy, so a user only downloads a page's code when they actually open that page.

Vite

8

Build tool and dev server

What it is
It turns our source files into files a browser can load, and runs a dev server that updates instantly as we change code.
Why we chose it
We wanted near-instant startup and reloads while we work, and fast production builds.
Alternatives we weighed
Create React App, hand-configured Webpack, Next.js.
Why ours won
Create React App was officially deprecated by the React team in 2025. Webpack felt slower and more complex than we wanted to configure. Next.js adds server-side rendering, which mostly helps search engines index pages — not much value for an app that lives behind a login.
In our code
Vite 8 uses Rolldown, a bundler written in Rust. Our whole client builds in about 7 seconds, with each page split into its own file.

Why we chose it

Alternatives we weighed
Next.js file-based routing, TanStack Router.
Why ours won
Next.js routing means adopting all of Next.js. TanStack Router looked strong but newer, with a smaller ecosystem than we wanted to depend on.

Backend and data

The server we built to store data and enforce every rule.

Node.js

≥ 20

Server runtime

What it is
It lets JavaScript run on a server instead of only inside a browser.
Why we chose it
We wanted one language across web, mobile and server. Its non-blocking design handles many requests waiting at once, which suits an API that spends most of its time waiting on the database.
Alternatives we weighed
Python with Django or FastAPI, Java with Spring Boot, Go.
Why ours won
All three are strong choices, but each would have added a second language and made us describe the same data twice. Node's known weakness is heavy number-crunching, which is exactly why we moved our heaviest computation, the analytics, into the browser.
In our code
We require Node 20 or newer, and our CI server job runs on Node 20.

Express

5.2

Web framework

What it is
A minimal framework that sends each incoming request through a chain of middleware to the right handler.
Why we chose it
It's the most widely used Node framework, with the biggest middleware ecosystem — and version 5 catches errors thrown inside async handlers for us automatically.
Alternatives we weighed
Fastify, NestJS, Koa.
Why ours won
Fastify wins raw speed benchmarks, but our bottleneck is the database, not request routing. NestJS felt like a heavy, Angular-style structure for our needs. Koa's ecosystem was far smaller than we wanted.
In our code
16 route modules, a 404 fallback for unknown routes, and one central error handler that returns a generic message and never leaks internal details.

MongoDB

via Mongoose

Database

What it is
A document database: each record is a flexible JSON-like document, not a row in a fixed table.
Why we chose it
Our workout data is naturally nested and varies by type. A strength entry holds a list of sets; a cardio entry holds pace, incline or cadence depending on the activity.
Alternatives we weighed
PostgreSQL, MySQL, Firebase Firestore.
Why ours won
Fixed relational tables would have needed a lot of mostly-empty columns or extra join tables to hold that variety. Firestore would have locked us into Google and charges per document read. And we didn't give up safety for it — MongoDB gives us full ACID transactions where we need them.
In our code
26 collections, 53 index declarations across 23 models, and a multi-document transaction for account deletion.
If we're pushed on it: "PostgreSQL stores JSON too." — True, and Postgres would have worked fine. We picked the database whose native model matched our data best. It's a question of fit for us, not a claim that Postgres couldn't do it.

Mongoose

9.7

ODM — schemas and validation

What it is
A layer that defines a schema for each collection and validates data before it saves.
Why we chose it
MongoDB on its own accepts anything. We wanted required fields, types, allowed values and defaults enforced for us.
Alternatives we weighed
The native MongoDB driver, Prisma, Typegoose.
Why ours won
The native driver has no schemas, so we'd have hand-written validation everywhere. Prisma's MongoDB support felt less mature than its SQL support. Typegoose needs TypeScript, which our server doesn't use.
In our code
We default profileVisibility to "private" in the schema itself — we enforce privacy at the data layer, not just in the interface.

Authentication

How we know who someone is.

JWT

jsonwebtoken 9

Login tokens

What it is
At login, we sign a token containing the user's id. The app sends it back to us with every request, and we check the signature to confirm it's genuine.
Why we chose it
It's stateless for us — no session table to look up — and one token covers our web app, our mobile app and our WebSocket connection.
Alternatives we weighed
Server-side sessions with cookies, hosted services like Auth0, Clerk or Firebase Auth.
Why ours won
Our web app on Vercel and our API on Render live on different domains, which makes cookie sessions harder for us to configure safely. Hosted auth services cost money at scale and hand user identity to a third party.
In our code
Our tokens expire after 7 days and travel in the Authorization: Bearer header. We reload the user from the database on every request, so deleting an account makes its token useless immediately.
If we're pushed on it: "You can't revoke a JWT." — A pure JWT can't be revoked before it expires, which is exactly why our middleware re-checks that the user still exists on every single request.

bcryptjs

3.0

Password hashing

What it is
It turns a password into an irreversible hash mixed with a random salt, and does it deliberately slowly.
Why we chose it
The slowness is the point for us. It makes trying millions of guessed passwords against a stolen database impractical.
Alternatives we weighed
Argon2, native bcrypt, scrypt, plain SHA-256.
Why ours won
Plain SHA-256 is far too fast for passwords. Native bcrypt needs a C++ compiler at install time, which fails on some hosts; bcryptjs is pure JavaScript and installs anywhere for us. Argon2 is the newer top recommendation, and bcrypt is still on OWASP's accepted list.
In our code
We use cost factor 10 — OWASP's minimum for bcrypt — so 2¹⁰ rounds of work go into every hash.
If we're pushed on it: "Why not Argon2?" — It's OWASP's first recommendation, and a sensible upgrade for us later. bcrypt at cost 10 is still an accepted choice today, and bcryptjs deploys with no native build step.

Reset links

Node crypto

Forgotten passwords

What it is
A one-time random link we email a user, which lets them set a new password.
Why we chose it
We only store a SHA-256 hash of the token, so even a database leak exposes no working reset links.
Alternatives we weighed
Storing the raw token, security questions, a hosted auth provider's reset flow.
Why ours won
A raw stored token would be usable by anyone reading our database. Security questions are guessable. A fast hash is fine here — unlike for passwords — because the token is long random data, not something a human chose.
In our code
Each link we send expires after 15 minutes and gets cleared the moment it's used.

Google sign-in

google-auth-library 10.7 · @react-oauth/google

"Continue with Google"

What it is
The React package shows Google's own sign-in button. Our server package verifies the resulting Google token is genuine and was issued for our app specifically.
Why we chose it
We didn't want to trust a token the browser merely claims came from Google — we check the signature and intended audience ourselves.
Alternatives we weighed
Passport.js, Firebase Auth, NextAuth.
Why ours won
Passport would have added a whole strategy framework for one provider. Firebase Auth means adopting Firebase. NextAuth is built for Next.js, which we don't use.
In our code
Google and email-password logins both end in the same 7-day Repvyn token, so the rest of our system never cares how someone signed in.

Security

The checkpoints we put in front of every request.

helmet

8.3

Security headers

What it is
It adds HTTP response headers that switch on protections already built into browsers.
Why we chose it
It stops browsers guessing file types, blocks our pages from being framed by other sites, enforces HTTPS, and hides that we run Express.
Alternatives we weighed
Writing each header ourselves, setting headers at a reverse proxy.
Why ours won
Hand-written headers get forgotten or misspelled over time. One well-maintained middleware covers the whole set for us.
In our code
We deliberately switch off Content Security Policy on our API. CSP protects pages that render HTML; our API returns JSON, and Vercel serves our HTML.

CORS

cors 2.8

Which sites may call our API

What it is
It tells browsers which websites we allow to call our API.
Why we chose it
It stops a malicious site from calling our API through a visitor's browser.
Alternatives we weighed
Allowing every site with *, putting frontend and API on one domain behind a proxy.
Why ours won
A wildcard would let any website call us. A same-domain proxy would add infrastructure we don't otherwise need.
In our code
In production we allow exactly one origin, read from our CLIENT_URL environment variable.

express-rate-limit

8.5

Abuse protection

What it is
It counts requests per client per time window and rejects anything over the limit with HTTP 429.
Why we chose it
It stops password guessing, spam posting and message flooding on our platform.
Alternatives we weighed
A Redis-backed limiter, Cloudflare or an API gateway, nginx rate limiting.
Why ours won
On our single server instance, counting in memory needs no extra infrastructure for us. Every alternative adds another service to run and pay for.
In our code
We run 12 limiters across 5 modules, each tuned to its action: login 10 per 15 minutes, forgot-password 5, posts 15 per hour, comments 30 per hour, chat messages 60 per 5 minutes. We can change any of these through an environment variable.
If we're pushed on it: "In-memory limits break with multiple servers." — Correct, each server would keep its own count. The same Redis step that lets us scale chat across servers also backs the rate limiter.

compression

1.8

Smaller responses

What it is
It gzip-compresses our API responses before we send them.
Why we chose it
Our JSON is highly repetitive text and compresses well — faster loads for users on slow mobile connections.
Alternatives we weighed
Compressing at a reverse proxy or CDN, Brotli compression.
Why ours won
Compressing inside our app behaves identically wherever we host it, with no platform-specific setup.

Media, email and push

Jobs we handed to specialised tools instead of building ourselves.

multer

2.2

Receiving file uploads

What it is
It reads multipart form data — the format browsers use to send files.
Why we chose it
Express can't read uploaded files on its own, so we needed something in front of it.
Alternatives we weighed
busboy, formidable, uploading straight from the browser to cloud storage.
Why ours won
busboy is the low-level parser multer is built on. formidable does similar work but felt less Express-native to us. Direct browser uploads would have skipped our own server-side checks on type and size.
In our code
Files stay in memory and never touch our server's disk. We cap uploads at 8 MB and only accept JPEG, PNG and WebP, before streaming them on to Cloudinary.

Cloudinary

2.10

Image storage and CDN

What it is
A hosted service that stores our images, transforms them, and serves them from servers around the world.
Why we chose it
We didn't want images consuming our API server's bandwidth or storage, and wanted them loading fast from nearby servers.
Alternatives we weighed
AWS S3 with CloudFront, Firebase Storage, saving files on our own server.
Why ours won
S3 plus CloudFront is two services we'd have had to wire together, with no built-in resizing. Firebase Storage would tie us to Google. And Render's filesystem is temporary, so anything we saved on our own server would be wiped on redeploy.
In our code
Uploads stream straight through. When an account is deleted, we destroy every one of its images after our database transaction succeeds.

Resend

6.19

Transactional email

What it is
An email-sending API for messages our app triggers, like password resets.
Why we chose it
We wanted a simple developer API with a free tier, and reliable delivery without running our own mail server.
Alternatives we weighed
SendGrid, Amazon SES, Nodemailer through Gmail.
Why ours won
SendGrid felt like a heavier platform for our one use case. Amazon SES starts in a sandbox we'd have to get lifted before emailing real users. A personal Gmail account has daily limits and tends to land in spam.

web push

web-push 3.6 · VAPID

Notifications

What it is
It delivers notifications to a user's browser even when Repvyn isn't open. VAPID is a key pair that proves the message really came from our server.
Why we chose it
It follows the open web standard, so we don't have Firebase code inside our app — each browser's own push service delivers the message.
Alternatives we weighed
Firebase Cloud Messaging, OneSignal.
Why ours won
Firebase would add Google's SDK to our app and tie delivery to Google. OneSignal is a third party that would see our notification data.
In our code
When a browser reports a subscription as gone — HTTP 404 or 410 — we delete it automatically.

Real-time

How we built instant chat.

ws

8.21

WebSocket server

What it is
A lightweight WebSocket server. Browsers connect to it using WebSocket support already built into them.
Why we chose it
We wanted chat messages to arrive instantly, without the app repeatedly asking us whether anything's new.
Alternatives we weighed
Socket.IO, polling, Server-Sent Events, Pusher or Ably.
Why ours won
Socket.IO layers its own protocol and client library on top of WebSockets. Polling wastes requests and adds delay. Server-Sent Events only flow from server to client. Pusher and Ably are paid services we didn't want to depend on.
In our code
We mount it at /ws/chat on the same server. We refuse a connection unless it carries a valid token for a user who still exists, and each user's messages reach every device they have open.
If we're pushed on it: "What happens with two servers?" — Today, the list of open connections lives in one server's memory, so a message received by server A can't reach a user connected to server B. Adding Redis pub/sub is our fix: every server subscribes to one channel and delivers to whoever it's holding.

Mobile — where we actually are

We're being direct about this one rather than letting the slide oversell it.

Where we actually stand: our mobile app is not a finished product yet. We built it to prove one specific thing end to end — that we could pull real data out of Android Health Connect and land it in our own database — and it does that. It's not something we'd hand a judge to install today. It runs as a custom development build through expo-dev-client, currently only on our own phone, and it needs a proper network connection to work. Turning it into an installable app for anyone else is our next milestone, not something already done.

supertest

7.2

API testing

What it is
It sends real HTTP requests to our Express app from inside our tests, without starting a network server.
Why we chose it
We wanted to test the full path a real client takes — middleware, authentication, validation and database.
Alternatives we weighed
Calling handler functions directly, Postman or Newman collections.
Why ours won
Calling handlers directly would skip middleware — exactly where security bugs hide. Postman collections live outside our codebase and aren't part of CI by default.

mongodb-memory-server

11.2

Real database for tests

What it is
It downloads and runs a genuine MongoDB server in memory for the length of a test run.
Why we chose it
We wanted tests running against real database behaviour, not imitations of it.
Alternatives we weighed
Mocking the database, a shared test database, MongoDB in Docker.
Why ours won
Mocks can pass even when real queries would fail. A shared database would let our tests interfere with each other. Docker would add a dependency to every developer machine and CI runner.

Playwright

1.62

End-to-end browser testing

What it is
It controls a real browser — clicking, typing, navigating — to test complete user journeys.
Why we chose it

Alternatives we weighed
Cypress, Selenium.
Why ours won
Cypress runs inside the browser and handles multiple tabs and cross-site flows awkwardly for us. Selenium felt slower and more verbose. Playwright covers Chromium, Firefox and WebKit, and waits for elements automatically.

Deployment and CI

Where we run this, and what guards every release we make.

Render

render.yaml

API hosting

What it is
A cloud platform that runs our Node server straight from our GitHub repository.
Why we chose it
We wanted our whole service described in one file, with automatic deploys and HTTPS included.
Alternatives we weighed
Heroku, Railway, AWS EC2 or ECS.
Why ours won
Heroku removed its free tier in 2022. Railway is comparable, but Render keeps our setup declarative in one committed file. AWS would mean managing our own servers, load balancers and certificates.
In our code
Our render.yaml defines the service and start command, and every secret is an environment variable, never written into our code.
If we're pushed on it: "Free tiers sleep." — Yes, honestly. Our API currently runs on Render's free plan, which sleeps when idle and cold-starts on the next request. Moving to a paid instance is a one-line configuration change for us, not a rewrite.

Vercel

vercel.json

Web app hosting

What it is
It hosts our built React app on a global edge network.
Why we chose it

GitHub Actions

ci.yml

Continuous integration

What it is
It runs automated jobs every time we push code.
Why we chose it
We wanted nothing reaching our main branch without passing the same checks, automatically, every time.
Alternatives we weighed
Jenkins, CircleCI, GitLab CI.
Why ours won
Jenkins needs its own server for us to maintain. CircleCI and GitLab CI are separate platforms, when our code already lives on GitHub.
In our code
We run three jobs on every push and pull request to main. Server: a syntax check of every file, then unit and integration tests on in-memory MongoDB. Client: lint, unit tests and a production build. End-to-end: Playwright browser tests that only run once both of the others pass.

Questions we've prepared for

The ones we think a technical judge is most likely to ask, with the honest answer we'd actually give. We'd rather admit a trade-off than get caught bluffing on one.

Where do you store the login token? Isn't localStorage insecure?

On the web, we keep it in localStorage. Its real risk is cross-site scripting — if someone injected a script into our page, it could read the token. Our mitigations: React escapes all rendered text by default, we use dangerouslySetInnerHTML zero times anywhere in our codebase, and our tokens expire after 7 days.

The alternative, an httpOnly cookie, hides the token from scripts but introduces cross-site request forgery risk — and because our site and API sit on different domains, it would need careful cross-site cookie configuration. It's a trade-off we know about, and moving to httpOnly cookies is a sensible hardening step we'd take next.

Is the mobile app actually usable?

Not yet, and we'd rather say that ourselves than have someone find out. It's a working prototype that proves the Health Connect pipeline end to end — phone sensor into our database — and it only runs on our own phone today, as a development build, over a proper network connection. Making it something we could hand anyone else to install is our next milestone, not something we're claiming is already finished.

Why MongoDB and not a SQL database?

Our data is document-shaped: a workout nests a variable list of sets, and cardio metrics differ completely by activity. Relational tables would need sparse columns or extra join tables for that. We don't lose integrity for it — MongoDB gives us full multi-document transactions, and we use one for account deletion.

How many users can it handle?

We haven't load-tested it yet, so we won't quote a number we can't back up. What we can say: our current ceiling is the hosting plan, not the design. Our authentication is stateless, our analytics run in the browser, our images come from a CDN, and our database is indexed. Our scaling path is clustering across CPU cores, then a paid instance, then multiple instances with Redis for chat and rate limits — measured properly with a load-testing tool like k6.

What breaks if you run two servers?

Two things we're aware of, both kept in one server's memory today: our list of open chat connections, and our rate-limit counters. Redis fixes both for us — pub/sub delivers chat messages across servers, and a shared store keeps one rate-limit count per user.

Where's the AI?

Deliberately absent. Every insight we generate is a transparent formula — the Epley equation for estimated one-rep max, a weighted fatigue score, percentile volume ranges — and each carries an evidence-strength tag. That makes every recommendation we give explainable, costs nothing to run, and can't hallucinate. We even deleted a feature ourselves whose evidence didn't meet our own bar.

Isn't Node.js bad at heavy computation?

Yes, and we know it — it's weak at long number-crunching on the server, which is exactly why we run our heavy analytics in the user's browser instead. Our server's job is mostly reading and writing the database, which is where Node's non-blocking design works in our favour.

Is it really a PWA, and does it work offline?

Not yet, and we'd rather be upfront about it. A PWA needs three things: HTTPS, a web app manifest, and a service worker. We have HTTPS and a service worker; we haven't added a manifest yet. Offline logging is designed but not built: we'll write each set into an IndexedDB queue and let Background Sync deliver it on reconnect, with a fallback for browsers without Background Sync support.

Worth knowing if a judge opens browser DevTools during our demo: our service worker today handles push notifications only. We'll say that ourselves rather than get caught by it.

What exactly happens when someone deletes their account?

One MongoDB transaction we wrote removes their data from 24 collections — workouts, goals, health data, follows, blocks, messages, posts, comments, reactions, notifications and more. If anything fails partway through, MongoDB rolls the whole thing back for us, so an account can never be left half-deleted. Only after it succeeds do we delete their images from Cloudinary, because Cloudinary can't take part in a database transaction.

How do you know any of this actually works?

GitHub Actions runs three jobs on every push we make: server tests against a real in-memory MongoDB, client linting plus unit tests plus a production build, and end-to-end tests in a real browser that only run after both of those pass. Nothing merges to our main branch unchecked.

Why not just build everything on Firebase?

Firebase would lock our authentication, database, storage and notifications into one vendor, with Firestore charging per document read. Owning our own schema is also what lets us enforce privacy defaults ourselves — like profiles starting private — at the data layer.

Why is wearable sync Android-only?

Health Connect is Android's system-level health hub, and Google is retiring its older Google Fit APIs in favour of it. iPhone support would mean adding an Apple HealthKit bridge that feeds the same backend models we already have — our server side wouldn't need to change.

Appendix: a few terms, for reference

Not the point of this document — just here in case a specific word needs pinning down.

REST endpoint
One request our API accepts, like GET /api/workouts to fetch workouts or POST /api/workouts to save one. We have 102.
Middleware
A checkpoint every request passes before it reaches our real logic — security headers, rate limits, login checks.
Collection
MongoDB's version of a table. We have 26.
Index
A lookup shortcut so our database finds records without scanning everything. We have 53.
ODM
Object Data Mapper: turns our database documents into JavaScript objects and validates them. Mongoose is ours.
Transaction
Database writes that all succeed together or all get undone. We use one for account deletion.
Replica set
Several MongoDB servers holding copies of the same data. MongoDB only allows transactions on one.
JWT
A signed pass we hand a user at login, which they show us on every later request.
Hashing vs encryption
Encryption reverses with a key. Hashing doesn't. We hash passwords, never encrypt them.
WebSocket
A connection that stays open so we can push messages instantly instead of polling.
CORS
A browser rule on which sites may call our API. We allow only our own, in production.
PWA
A site with a manifest file and a service worker, installable and offline-capable. We're not there yet.
Service worker
A background script apart from the page. Ours currently handles push notifications.
IndexedDB
A real, structured database built into every browser, usable while offline.
Unit, integration, E2E
Unit tests check one function, integration tests check pieces together, end-to-end drives a real browser.
Stateless
Our server keeps no login memory between requests — each request proves itself with its own token.
